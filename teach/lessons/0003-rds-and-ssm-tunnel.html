RDS & the SSM Tunnel

Why psql can't reach the database directly, and what that aws ssm start-session ... PortForwarding command in docs/rds-bootstrap.md is actually doing. Builds on Lesson 2.

Quick recap of where the first two lessons left you, because this lesson leans on all of it: a VPC is one private address space, split into subnets. A subnet is "public" only if its route table sends 0.0.0.0/0 traffic to an internet gateway — otherwise it's private and unreachable from outside (Lesson 1). The bastion sits in the public subnet, has no inbound ports open at all, and you still reach it because its SSM agent makes an outbound connection to AWS, which relays your session in (Lesson 2). This lesson is about the last hop: from that bastion shell to an actual Postgres database sitting in a private subnet — and why the real command you run isn't a shell session at all.

1. RDS instance — a database AWS runs for you

RDS (Relational Database Service) is AWS operating a database engine (here, Postgres) on your behalf — patching, backups, storage all handled — while you still get a normal Postgres endpoint to connect to. In rds.tf:

resource "aws_db_instance" "main" {
  engine               = "postgres"
  db_subnet_group_name = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.rds.id]
  publicly_accessible  = false
}

publicly_accessible = false is the headline: this database gets no public IP, full stop. That's not paranoia — a database is exactly the kind of thing a bastion exists to protect (Lesson 2, "why not just open the database's port to the internet?").

DB subnet group — which subnets RDS is allowed to live in

resource "aws_db_subnet_group" "main" {
  subnet_ids = [aws_subnet.private_a.id, aws_subnet.private_b.id]
}

RDS doesn't let you point it at one specific subnet — you hand it a group of subnets (here, both private ones, in different Availability Zones per Lesson 1) and AWS places the instance in one of them, keeping the option to fail over to another AZ later. Both are private: no route to an internet gateway, so nothing about this changes the "no public IP" story.

2. RDS's security group — this is the new piece

resource "aws_security_group_rule" "rds_from_bastion" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  security_group_id        = aws_security_group.rds.id
  source_security_group_id = aws_security_group.bastion.id
}

Lesson 2's bastion security group had plain CIDR blocks (0.0.0.0/0 for egress). This rule is different: instead of "allow traffic from this IP range," it says "allow traffic from anything wearing the bastion's security group." source_security_group_id doesn't care what subnet the bastion is in or what its IP is — it's an identity check, not a location check. If the bastion gets replaced tomorrow with a new IP address, this rule still works unchanged, because it's still the same security group attached.

Two locks on the same door

Port 5432 (Postgres) is only reachable by things carrying the bastion's security group or the generator's (see rds_from_generator — same pattern, different source). Every other source, including your laptop's IP, is refused before a single byte of Postgres protocol is exchanged. This is enforced by AWS's network layer, before it ever reaches the database.

3. The actual problem: your laptop isn't in the VPC

Put the last two lessons together and a puzzle appears. The bastion can reach RDS — it's in the VPC, private routing between subnets is always on (Lesson 2), and the security group allows it. But you, running psql on your laptop, are not in the VPC. You have no route to 10.0.0.0/16 at all — your laptop doesn't even know that address space exists. Getting an SSM shell on the bastion (Lesson 2) would let you run psql from inside it — but that means installing a Postgres client on a box meant to stay minimal, every time. There's a better way: make the bastion carry your bytes for you, without you ever getting a shell on it.

4. SSM port forwarding — a tunnel, not a shell

Lesson 2 covered one SSM document: AWS-StartInteractiveCommand-style shell sessions. There's a second one, AWS-StartPortForwardingSessionToRemoteHost, and it's the one docs/rds-bootstrap.md actually uses:

aws ssm start-session \
  --target "$INSTANCE_ID" \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["'"$RDS_HOST"'"],"portNumber":["5432"],"localPortNumber":["15432"]}'

This doesn't give you a shell on the bastion at all. Instead it opens a local port on your machine (15432) and pipes anything sent to it, through the same outbound SSM control channel from Lesson 2, to the bastion, which forwards it onward to $RDS_HOST:5432. The bastion is acting purely as a relay — it never runs psql, never sees your query, doesn't even need Postgres installed. It's just proving, via its security group membership, that it's allowed to speak to port 5432 on that host — and lending you that permission for the duration of the tunnel.

Why this, and not just SSH port forwarding?

Same "no inbound ports" property as Lesson 2's shell session: the tunnel rides the SSM agent's existing outbound connection. No SSH key to manage, no port 22 to open on the bastion, and every session is logged and IAM-governed like any other SSM action.

Once that's running (you'll see Waiting for connections...), localhost:15432 on your laptop is, for practical purposes, a direct line to the database:

psql -h localhost -p 15432 -U steam_proj_admin -d steam

psql has no idea a tunnel exists. It thinks it's talking to a normal Postgres server on localhost. Everything past that command — the private routing, the security group check, the relay through the bastion — is invisible to it.

Putting the whole path together

your laptop AWS ┌──────────────┐ outbound SSM channel ┌─────────────────────┐ │ psql │──────────────────────────▶│ Systems Manager │ │ → localhost: │ (Lesson 2's agent │ (control plane) │ │ 15432 │ connection, reused) └──────────┬───────────┘ └──────────────┘ │ relays to bastion ▼ ┌───────────────────────── VPC ─────────────────────────────────┐ │ public subnet │ │ ┌─────────────┐ security group: bastion → allowed on 5432 │ │ │ bastion │ (identity-based rule, Section 2) │ │ │ (pure relay, │ │ │ │ no psql) │ │ │ └──────┬───────┘ private VPC routing (always on, Lesson 2) │ │ ▼ │ │ private_a / private_b │ │ ┌─────────────┐ │ │ │ RDS Postgres │ publicly_accessible = false │ │ │ port 5432 │ reachable only from bastion + generator SGs │ │ └─────────────┘ │ └───────────────────────────────────────────────────────────────┘

Three independent layers had to line up for that one psql command to work: the network (RDS lives in a private subnet reachable from the bastion via always-on VPC routing), the security group (an identity-based rule naming the bastion's SG, not an IP range), and the tunnel (SSM port forwarding, riding the same outbound-only agent connection from Lesson 2, so your laptop never needs a route into the VPC at all).

Check yourself

Q1. Why does rds_from_bastion use source_security_group_id instead of a CIDR block?
Reveal answer
Identity-based, survives IP changes.
Q2. When the tunnel is open and you run psql -h localhost -p 15432, does the bastion ever run Postgres client code?
Reveal answer
No, it only relays raw bytes.
Q3. Could you skip the bastion and point psql straight at the RDS endpoint from your laptop?
Reveal answer
No, not public and no route.
