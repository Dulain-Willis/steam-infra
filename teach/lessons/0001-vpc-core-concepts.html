VPC Core Concepts

The raw AWS networking ideas behind your steam-infra network.tf — no Terraform, just the concepts.

Your Terraform builds six things. Each one is a real AWS concept that exists whether or not Terraform is in the picture. Here's what each one is, stripped of syntax.

1. VPC — your own private network inside AWS

A VPC (Virtual Private Cloud) is an isolated slice of network space that belongs only to you. Nobody else's AWS resources can see into it unless you explicitly connect them. Think of it as your own private building — AWS owns the land (the region), the building and everything in it is yours.

A VPC is defined by an IP address range, written in CIDR notation:

cidr_block = "10.0.0.0/16"
CIDR, decoded

10.0.0.0/16 means: the first 16 bits of the address are fixed (10.0), the remaining 16 bits are yours to allocate. That's 216 = 65,536 IP addresses available inside this VPC.

10.0.0.0/24 (used later for a subnet) fixes 24 bits, leaving 8 bits free = 256 addresses.

Smaller number after the slash = bigger range. Backwards from what most people guess first.

10.0.0.0/16 falls inside RFC 1918 private address space — not routable on the public internet, by design. Nothing outside your VPC can reach these addresses directly, regardless of any gateway you attach.

The two DNS flags just turn on Amazon's internal DNS resolver inside the VPC and let instances get hostnames — housekeeping, not core to the network shape.

2. Availability Zones — physically separate datacenters

Before subnets make sense: an Availability Zone (AZ) — like us-east-1a — is a physically distinct datacenter (or cluster of them) within an AWS region, with its own power, cooling, network. AZs in the same region are close enough for fast, cheap connections between them, but far enough apart that one catching fire doesn't take out the other.

This is why your Terraform has private_a in us-east-1a and private_b in us-east-1b: fault isolation. If one datacenter has a bad day, the other keeps running.

3. Subnets — slices of the VPC, pinned to one AZ

A subnet is a sub-range carved out of the VPC's IP space, and — this is the part that trips people up — every subnet lives in exactly one Availability Zone. You can't spread a single subnet across two AZs. "High availability across AZs" always means "more than one subnet."

VPC 10.0.0.0/16 (65,536 addresses, spans the whole region) │ ├── public 10.0.0.0/24 us-east-1a (256 addresses) ├── private_a 10.0.1.0/24 us-east-1a (256 addresses) └── private_b 10.0.2.0/24 us-east-1b (256 addresses)

Nothing about a subnet's name makes it "public" or "private" — that word in your resource name (aws_subnet.public) is just a label you chose. What actually determines public vs. private is section 5 below.

4. Internet Gateway — the door to the internet

An Internet Gateway (IGW) is a horizontally-scaled, AWS-managed component attached to your VPC that does exactly one job: give traffic a path in and out of the public internet. No IGW attached, no VPC resource can ever talk to the internet, full stop — no matter what else is configured.

resource "aws_internet_gateway" "gw" {
  vpc_id = aws_vpc.main.id
}

Attaching an IGW doesn't automatically expose anything. It just makes the internet reachable — something else has to point traffic at it. That's the route table's job.

5. Route tables — the actual definition of "public"

A route table is a list of rules: "traffic headed to this destination goes out that door." Every subnet is associated with exactly one route table, and that table decides where the subnet's outbound traffic can go.

route {
  cidr_block = "0.0.0.0/0"
  gateway_id = aws_internet_gateway.gw.id
}

0.0.0.0/0 means "any destination not otherwise matched" — i.e. the internet. This rule says: anything leaving this subnet that isn't destined for somewhere else inside the VPC, send it out through the Internet Gateway.

This is the actual public/private boundary

A subnet is "public" purely because its route table has a 0.0.0.0/0 → igw route. private_a and private_b have no route table of their own defined here, so they fall back to the VPC's default ("main") route table — which has no route to the internet. That's the entire mechanism. Nothing else makes a subnet public.

The map_public_ip_on_launch = true flag on the public subnet is a separate, complementary setting — it auto-assigns a public IP to any instance launched there. Without a route to an IGW, that public IP would be useless. With it, the instance is actually reachable.

6. Route table association — wiring the subnet to the table

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

This is the explicit link. A VPC always has an implicit main route table that every subnet uses by default (no internet route, private by default). This association overrides that default for the public subnet only, pointing it at the custom route table with the IGW rule instead. private_a and private_b have no association, so they silently stay on the private-by-default main table.

Putting it together

Internet │ ▼ Internet Gateway (gw) │ ▼ (only via a route table entry) ┌─────────────────────────────────────────────┐ │ VPC 10.0.0.0/16 │ │ │ │ public subnet (10.0.0.0/24, us-east-1a) │ │ └─ route table: 0.0.0.0/0 → gw (explicit)│ │ │ │ private_a (10.0.1.0/24, us-east-1a) │ │ └─ main route table (no internet route) │ │ │ │ private_b (10.0.2.0/24, us-east-1b) │ │ └─ main route table (no internet route) │ └─────────────────────────────────────────────┘

Check yourself

Q1. If you deleted the route_table_association for "public" but left everything else, would instances in that subnet still reach the internet?
Reveal answer
No, it falls back to the main table.
Q2. Could private_a and private_b share one single subnet instead of two?
Reveal answer
No, one subnet spans one zone.
Q3. What actually makes the "public" subnet public, in one phrase?
Reveal answer
Its route table has an internet route.
