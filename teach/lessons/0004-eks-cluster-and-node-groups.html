EKS Cluster & Node Groups

PR #39: terraform/eks.tf and the two new subnets in network.tf. Builds on Lesson 1 (subnets, route tables).

Your read on the subnet/route-table mechanics in this PR is already correct — this lesson confirms that quickly, then spends most of its time on the part that's actually new: EKS node groups, taints, and why the cluster config has two of everything.

1. What you already had right

network.tf adds two subnets, eks_a (10.0.10.0/24) and eks_b (10.0.11.0/24). /24 = 256 addresses, correct. Each is a plain aws_subnet — nothing about it is "public" by itself.

resource "aws_route_table_association" "eks_a" {
  subnet_id      = aws_subnet.eks_a.id
  route_table_id = aws_route_table.public.id
}

This association is what makes them public — it's the same aws_route_table.public that Lesson 1's original public subnet already uses, the one with the single 0.0.0.0/0 → igw route. No new route table was created; these two subnets just got wired into the existing one. Your mental model (association = the wire between subnet and route table, route table = the rules, 0.0.0.0/0 = "yes, internet") is exactly right.

Why public subnets, with no NAT gateway?

The PR body says it explicitly: no NAT gateway, so map_public_ip_on_launch = true and a route to the internet gateway is the only way these worker nodes can reach the internet at all — to pull container images, talk to the EKS control plane, etc. It's a cost/complexity tradeoff (NAT gateways aren't free), not an oversight.

2. The one genuinely new tag: kubernetes.io/role/elb

tags = {
  Name                     = "steam-infra-eks-a"
  "kubernetes.io/role/elb" = "1"
}

This isn't an AWS mechanism — it's a convention that Kubernetes' own tooling reads. When something in the cluster asks for a LoadBalancer-type Service (say, exposing a Kafka Connect REST API to the internet later), the controller that provisions the actual AWS load balancer doesn't know which of your subnets are safe to put it in. It finds out by scanning your VPC's subnets for this exact tag. kubernetes.io/role/elb = 1 says "this is a candidate subnet for a public-facing load balancer"; the equivalent for internal ones is kubernetes.io/role/internal-elb. No tag, no auto-discovery — the load balancer controller would have nothing to place resources into.

So the tag exists for the same reason the subnets are public: it's Kubernetes tooling, running inside the cluster later, reaching back out into raw AWS resources it doesn't otherwise have a config file pointing at.

3. The EKS module, field by field

eks.tf wraps the community terraform-aws-modules/eks/aws module, which is generating dozens of underlying resources (IAM roles, security groups, the control plane itself) from a much smaller set of inputs you actually write:

FieldWhat it controls
cluster_name, cluster_versionName AWS assigns to the control plane, and which Kubernetes version it runs.
vpc_id, subnet_idsWhich network the control plane and nodes live in — the two subnets from Section 1.
cluster_endpoint_public_accessWhether the Kubernetes API server (the thing kubectl talks to) has a public endpoint at all, separate from whether the worker nodes have public IPs.
authentication_modeHow AWS IAM identities map to Kubernetes users. "API" means that mapping lives in an AWS-native API instead of a Kubernetes ConfigMap you'd otherwise have to edit by hand.
enable_cluster_creator_admin_permissionsWhoever runs terraform apply automatically gets cluster-admin — convenience for a small team, one line instead of a separate access-entry resource.
eks_managed_node_groupsThe actual EC2 worker pools — Section 4.

4. Node groups: why two, not one

An EKS managed node group is a pool of EC2 instances that AWS provisions, joins to your cluster, and keeps at your desired count automatically — you describe the pool, not each machine. This PR defines two:

system = {
  instance_types = ["t3.medium"]
  min_size = 1, max_size = 3, desired_size = 2
}

kafka = {
  instance_types = ["m5.large"]
  min_size = 3, max_size = 3, desired_size = 3
  labels = { role = "kafka" }
  taints = { kafka = { key = "dedicated", value = "kafka", effect = "NO_SCHEDULE" } }
}

Every Kubernetes cluster needs some baseline capacity for cluster-wide plumbing — DNS, logging agents, the load-balancer controller from Section 2, and so on. That's system: general-purpose, cheap, autoscaling instances (t3.medium, burstable, 1–3 nodes). It's deliberately generic because it's meant to host whatever shows up.

kafka exists because Kafka brokers have needs the system pool doesn't guarantee: a fixed, predictable node count (min = max = desired = 3, no autoscaling — brokers care about stable identity, not elastic scale-to-zero), and beefier steady-state instances (m5.large, not burstable). Mixing that in with whatever else lands on system risks a random pod eating the CPU or memory a broker needs, or an autoscaler evicting a node a broker was pinned to. Separate pool, separate guarantees.

5. Taints and labels — the two-sided handshake that keeps them separate

Having two node groups isn't enough by itself — by default, Kubernetes' scheduler will happily drop any pod onto any node with room, including your Kafka nodes. Taints and labels are the two independent mechanisms that stop that.

Label — an opt-in, not an enforcement

labels = { role = "kafka" } just stamps every node in this group with role=kafka. On its own it does nothing — it's descriptive metadata. A Kafka pod would separately need a nodeSelector: { role: kafka } in its own spec to actually request landing there. Labels answer "where do I want to go?"

Taint — a repel, not an attract

taints = { kafka = { key = "dedicated", value = "kafka", effect = "NO_SCHEDULE" } } does the opposite job: it marks every node in this group as off-limits to everything, by default. NO_SCHEDULE means the scheduler won't place a new pod here unless that pod carries a matching toleration — a clause in its own spec saying "I tolerate the dedicated=kafka taint." No toleration, no placement, full stop. Taints answer "who's allowed to land on me?"

Put together: the label is how a Kafka pod finds these nodes; the taint is what keeps every other pod off them. You need both — a label alone wouldn't stop a random pod from landing here anyway, and a taint alone wouldn't tell Kafka pods where to go. The system group has neither, which is exactly why it's the default landing spot for anything that doesn't ask for somewhere specific.

Check yourself

Q1. What makes eks_a and eks_b public subnets rather than private ones?
Reveal answer
Route table association to public.
Q2. A pod with no taints or tolerations gets scheduled. Which node group can it land on?
Reveal answer
Only the system node group.
Q3. Does the label alone stop other pods from landing on the kafka nodes?
Reveal answer
No — only the taint does.
