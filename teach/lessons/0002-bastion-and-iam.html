The Bastion & IAM

What a bastion actually is, and how identity (IAM) lets it act — mapped to bastion.tf. Builds on Lesson 1.

Lesson 1 built the network: a public subnet with a route to the internet, and two private subnets with none. A private subnet with no internet route is exactly where you'd put a database — nobody outside can reach it directly. But that raises a problem: how do you reach it, to run a migration or check a row?

That's what a bastion is for.

1. Bastion host — a guarded doorway into the private network

A bastion host (also called a "jump box") is a single, deliberately minimal server that sits in a public subnet and acts as the one sanctioned entry point into the rest of the VPC. Instead of exposing your database to the internet, you expose one small, tightly-locked-down instance instead — and everything private gets reached through it, over the private network inside the VPC.

Why not just open the database's port to the internet?

Every open port facing the internet is a thing that gets scanned and attacked within minutes of existing. A bastion shrinks your entire internet-facing attack surface down to one small, purpose-built box you can lock down hard — instead of every service having its own exposed door.

Your bastion lives in the public subnet from Lesson 1:

subnet_id                   = aws_subnet.public.id
associate_public_ip_address = true

It needs to be reachable from outside (that's the whole point), so it sits where the internet route exists. A database in private_a has no such route — but the bastion, sitting inside the same VPC, can still reach it directly over the private 10.0.0.0/16 address space. The VPC's internal routing between subnets is automatic and always on; only the internet route is the special, opt-in part.

2. Security group — a stateful firewall glued to the instance

A security group is a virtual firewall attached directly to an instance (technically to its network interface). It's a set of allow-rules — nothing is permitted unless a rule says so. Unlike a route table (which controls where traffic can go), a security group controls what traffic is allowed to actually flow, in and out.

resource "aws_security_group" "bastion" {
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

Notice what's missing: there's no ingress block at all. This security group allows all outbound traffic (ports 0-0 with protocol -1 means "any port, any protocol") and zero inbound traffic. No SSH port 22, nothing. That looks broken for a bastion — how do you log into a box with no open inbound ports? Section 4 answers that.

Security group vs. route table — don't conflate these

Route table: "can this traffic reach its destination at all?" (Lesson 1) Security group: "is this specific instance willing to accept/send this traffic?" A packet has to clear both to actually arrive. They're independent layers.

3. IAM role — a set of permissions something can temporarily assume

Separate from networking entirely: how does the bastion get permission to do AWS things (like talk to the Systems Manager service)? That's IAM (Identity and Access Management).

An IAM role is a set of permissions that isn't permanently owned by anyone — it's assumed temporarily by whoever is trusted to assume it. Contrast with an IAM user, which is a permanent identity with its own long-lived credentials. A role has no credentials of its own; something else proves it's allowed to wear the role, then gets temporary access.

data "aws_iam_policy_document" "bastion_assume" {
  statement {
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["ec2.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "bastion" {
  assume_role_policy = data.aws_iam_policy_document.bastion_assume.json
}

This block is called a trust policy: it says "the EC2 service itself is allowed to assume this role." It's not about what the role can do yet — it's about who's allowed to put on the role in the first place. Here, that's any EC2 instance this role gets attached to.

4. Managed policy — what the role can actually do

resource "aws_iam_role_policy_attachment" "bastion_ssm" {
  role       = aws_iam_role.bastion.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"
}

Trusting who can assume a role (step 3) is separate from granting that role actual permissions. AmazonSSMManagedInstanceCore is an AWS-maintained managed policy — a pre-written bundle of permissions AWS keeps updated for you. This one grants exactly the permissions needed for the SSM (Systems Manager) Agent running on the instance to register itself and accept commands from AWS.

This is the answer to the "no inbound ports" puzzle from section 2: instead of you connecting in to the bastion over SSH, the SSM agent on the bastion connects out to AWS's Systems Manager service. When you want a shell, you run aws ssm start-session — AWS relays your session to the agent over that outbound connection. No inbound port ever opens.

5. Instance profile — the wrapper EC2 actually attaches

resource "aws_iam_instance_profile" "bastion" {
  role = aws_iam_role.bastion.name
}

This one's pure AWS plumbing, not a separate concept: an EC2 instance can't attach an IAM role directly — it attaches an instance profile, which is a thin wrapper holding exactly one role. Terraform makes this look like an extra resource; on the ground it's really just "the container that lets an EC2 instance carry a role."

6. AMI — the disk image the instance boots from

data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-*-arm64"]
  }
}

An AMI (Amazon Machine Image) is a snapshot of a bootable disk — OS plus whatever's baked in. This isn't creating anything; it's a lookup ("find me the newest Amazon Linux 2023 image built for arm64 chips") so the instance always boots on a current, patched image without you hunting down an ID by hand.

Putting it together

You, running: aws ssm start-session │ ▼ AWS Systems Manager (control plane) ▲ │ outbound only — agent-initiated ┌─────────────────────────────────────────────────────────┐ │ VPC │ │ │ │ public subnet (10.0.0.0/24) │ │ ┌─────────────────────────┐ │ │ │ bastion instance │ ← IAM role (via instance │ │ │ - security group: │ profile) grants SSM │ │ │ no inbound, all outbound│ permissions │ │ └────────────┬───────────┘ │ │ │ private VPC routing (always on) │ │ ▼ │ │ private_a / private_b subnets — e.g. a database here │ │ (reachable from the bastion, not from the internet) │ └─────────────────────────────────────────────────────────┘

Four independent layers stack up to make this work: the network (which subnet, which route table — Lesson 1), the security group (which traffic is allowed to/from this instance), the IAM role (what AWS-API actions this instance is permitted to call), and the AMI (what's actually running on it). None of these substitute for each other — a hole in one doesn't get patched by the others.

Check yourself

Q1. Why does the bastion's security group have zero inbound rules, yet you can still get a shell on it?
Reveal answer
SSM connects outbound, not inbound.
Q2. If you deleted the IAM role policy attachment but kept everything else, could you still reach the bastion via SSM?
Reveal answer
No, agent loses required permissions.
Q3. Could the bastion reach a database sitting in private_a, given everything in this lesson?
Reveal answer
Yes, private routing is always on.
